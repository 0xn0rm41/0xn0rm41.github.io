Overview

Embedded devices — routers, cameras, IoT — run stripped-down Linux on MIPS or ARM and routinely ship with hardcoded credentials, shared private keys, and backdoor accounts baked into the firmware image. Extracting and auditing firmware is a standard methodology in IC hardware analysis, product security research, and CVE discovery.

Target: a simulated TP-Link style firmware image with realistic structure — vendor header followed by a gzip-compressed SquashFS filesystem. The complete triage workflow was executed from raw binary to credential extraction using binwalk, dd, and unsquashfs.

Phase 1 — binwalk Identification

binwalk firmware.bin

DECIMAL HEXADECIMAL DESCRIPTION
──────────────────────────────────────────────────────────────
64 0x40 SquashFS filesystem, little endian,
version 4.0, compression: gzip,
inode count: 13, block size: 131072,
image size: 734 bytes

Three immediate findings from binwalk output alone — before a single byte is extracted: the filesystem type (SquashFS 4.0), the compression algorithm (gzip), and the byte order (little-endian — MIPS-LE or ARM-LE device). The offset 0x40 tells us exactly where to cut with dd.

⚡ Little-Endian vs Big-Endian

TP-Link's older MIPS devices are big-endian. Newer designs and most ARM devices are little-endian. Endianness determines which IDA processor module to select when opening extracted binaries — wrong endian = unreadable disassembly.

Phase 2 — Extraction

binwalk's sasquatch extractor was unavailable. Manual extraction using known offset — a more reliable approach for non-standard firmware layouts:

extraction
# Skip vendor header (64 bytes = 0x40), extract raw SquashFS
dd if=firmware.bin of=rootfs_raw.sqfs bs=1 skip=64

# Extract filesystem
unsquashfs rootfs_raw.sqfs

# Result: squashfs-root/ containing full device filesystem
Manual Extraction — When binwalk Fails

When automatic extraction fails, the offset from binwalk output is all that's needed. dd skip=N cuts the blob at any byte boundary. This works on any firmware regardless of vendor header format.

Phase 3 — Credential Triage

Four commands covering the standard firmware credential hunt. In real firmware this grep pass has found live CVEs in minutes.

credential hunt commands
# Passwd files
find . -name "passwd" 2>/dev/null

# Base64 tokens
grep -r "==" . 2>/dev/null | grep -v Binary

# Hardcoded passwords in binaries
grep -r "password" . 2>/dev/null | grep -v Binary

# Basic Auth headers
grep -r "Basic" . 2>/dev/null | grep -v Binary

# Private keys
find . -name "*rsa*" -o -name "*dropbear*" -o -name "*.key" 2>/dev/null

Findings

Cleartext Credential in passwd
/etc/passwd
Critical

Two accounts discovered:

root:$1$abc123$hashvalue:0:0:root:/root:/bin/sh   ← MD5-crypt, crackable
admin:admin:1000:1000::/home/admin:/bin/sh        ← cleartext, no hashing
The admin:admin entry stores a cleartext password directly in the passwd file — no shadow file, no hashing. The $1$ prefix on root indicates MD5-crypt, trivially crackable offline with hashcat and a standard wordlist. Both accounts survive factory reset as they are baked into the firmware image.
Shared SSH Private Key
/etc/dropbear_rsa_host_key
Critical
A private RSA host key is embedded in the firmware image. Every device flashed with this firmware version shares the identical private key. An attacker who extracts this key from one physical device can impersonate the SSH server of every other device running this firmware globally — trivially defeating host verification. This exact vulnerability class has produced real CVEs across multiple vendors including Juniper, Cisco, and numerous consumer router manufacturers.
Hardcoded Admin Password in Web Server Binary
/usr/bin/httpd
Critical
password=tplink123 found as a plaintext string in the httpd binary. Hardcoded credentials in the web admin binary bypass any password change made through the UI — the backdoor credential persists regardless of user configuration. Extracted via grep -r "password" without disassembly.
Hardcoded Basic Auth Header
/usr/bin/httpd
High
Authorization: Basic YWRtaW46YWRtaW4= found embedded in the httpd binary. Base64 decode confirms: admin:admin — the same credential present in passwd, hardcoded a second time as a pre-built HTTP Basic Auth header. This suggests the binary is designed to make outbound authenticated requests using a fixed credential — potentially to a management server or C2.

What I Learned

01 — binwalk Offset Is All You Need

When automatic extraction fails, the decimal offset in binwalk output is enough. dd skip=N cuts any firmware blob at any boundary — no special tooling required.

02 — Shared Keys Are a Global Vulnerability

A private key embedded in firmware affects every device on that firmware version simultaneously. One physical device extraction compromises the entire deployed fleet — no network access required for the key theft.

03 — Factory Reset Doesn't Clear Firmware Credentials

Credentials baked into the firmware image survive factory reset — they're not stored in user-writable flash. Any backdoor in /etc/passwd or a binary persists across resets by design.

04 — grep Before Disassembly

Four critical findings surfaced from grep alone — no disassembly, no dynamic analysis. String search is always the first pass on extracted firmware. Disassembly is the follow-up for findings that need context.

05 — Base64 Is Not Encryption

YWRtaW46YWRtaW4= looks opaque in a binary but is trivially decoded. Base64 encoding provides zero confidentiality — it's encoding, not encryption. Any credential stored in base64 is effectively cleartext.

06 — Endianness Determines Disassembler Config

Little-endian SquashFS means a little-endian CPU — MIPS-LE or ARM-LE. Loading a big-endian MIPS binary into IDA as little-endian produces unreadable disassembly. binwalk's endian flag is the first thing to check before opening IDA on extracted binaries.
