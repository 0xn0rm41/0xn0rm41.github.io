Overview

The majority of real-world implants, RATs, and malware target Windows and ship as PE files. Before a single instruction is disassembled, a structured static triage extracts identity, capability, and anomaly information in under two minutes. This writeup documents that full workflow applied to putty.exe (v0.82) — a real, complex, non-trivial PE used as a known-good training target.

Environment: FlareVM (Windows 10 VM, snapshotted), PEStudio, IDA Pro 9.1.

Phase 1 — PEStudio Triage

Identity & Timestamp

The compile timestamp reads Sat 01 Feb 2025 11:27:15 — consistent with PuTTY 0.82's public release date. In malware analysis, timestamps are the first thing scrutinized. Forged timestamps are a common anti-forensics technique: values of 1970-01-01, dates far in the future, or timestamps that exactly match a legitimate binary's are all immediate red flags.

⚡ Timestamp Forgery Patterns

1970-01-01 — zeroed timestamp, compiler flag or deliberate wipe  ·  2037+ — future date, clearly fabricated  ·  Exact match to known binary — cloning legitimate metadata to evade detection

Entry Point

Entry point at 0x000A1086 falls within the .text section — correct and expected. Code lives in .text. An entry point landing in .data, .rsrc, or a strangely named section like .UPX0 or .pack is a strong packer indicator — the real code is hidden and the entry point points at a stub that unpacks it at runtime.

The compiled HTML help resource reads 7.9 entropy — near-maximum. This is legitimately expected: .chm files are compressed archives, and compressed data is statistically indistinguishable from encrypted data to an entropy scanner. The analyst decision is: is this high entropy in a known compressed resource, or in executable code? Here it's the former — expected and benign.

⚠ Entropy Decision Rule

High entropy in .rsrc or a named help resource → expected compression, note and move on.
High entropy in .text, .data, or an unnamed section → likely packed or encrypted payload → unpack before continuing.

Suspicious Imports — Capability Fingerprint

The import table is the fastest behavioral signal before any disassembly. The following imports would raise immediate flags in a malware context:

OpenProcess Precursor to process injection — gain handle to target process Security query (SID lookup)

Phase 2 — IDA Import Xref Pivot

PEStudio identifies suspicious imports. IDA answers the follow-up question: where is each import called from, and what is the surrounding context? The xref pivot (X in IDA) is the core analysis loop.

IDA — xref workflow
Imports window → select suspicious function
      ↓
X  (xref) → list all callers
      ↓
Read caller context → interactive UI code or autonomous background code?
      ↓
N  → rename function to document intent
      ↓
Repeat for next import

Function Naming Discipline

Renaming functions as analysis progresses is non-negotiable in long sessions. The naming convention used throughout:

PatternExampleRationale
verb_object get_process_sid Describes action and target — unambiguous after hours of analysis
intent over mechanism establish_persistence not write_regkey When intent is established, name the purpose not the implementation
snake_case lowercase inject_shellcode Matches how findings are written in analyst reports
never abbreviate open_or_create_regkey not ocrk Abbreviations become meaningless in 24 hours

What I Learned

01 — Imports Are a Capability Map

The import table tells you what a binary can do before you read a single instruction. Clustering dangerous imports — OpenProcess + VirtualAllocEx + WriteProcessMemory — is a near-certain injection signal.

02 — Entropy Requires Context

High entropy alone is not a finding. The same 7.9 reading means "compressed help file" in a legitimate binary and "encrypted payload" in malware. The section name and type determine which interpretation is correct.

03 — Xref Context Is Everything

A dangerous import called once from a dialog handler is benign. The same import called three times from anonymous background functions is malicious. The number of xrefs and their calling context are the actual signal.

04 — Timestamps Are Unreliable

PE compile timestamps can be set to any value by the compiler or a hex editor. They are a hint, not evidence. Plausibility check only — never anchor a conclusion on a timestamp alone.

05 — Entry Point Location Reveals Packing

Legitimate code enters at .text. An entry point in .data, .rsrc, or an unnamed section means a packer stub is running first. The real code is hidden and must be unpacked before analysis.

06 — Name As You Go

Renaming sub_439040 to open_or_create_regkey the moment you understand it prevents re-reversing the same function later. Every analysis session builds a database of named functions — treat it as a living document.
