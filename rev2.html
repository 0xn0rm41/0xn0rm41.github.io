Indirect Jumps & Obfuscation

Recovering control flow from a function pointer dispatch table — static and dynamic analysis paths.

Overview

The target binary validates input through four separate check functions dispatched via a function pointer table. The core challenge: the call inside the validation loop is call eax — an indirect jump — which breaks IDA's static call graph and is the same technique used in real-world packers, loaders, and malware to resist static analysis.

The goal was to recover all four constraints using both static and dynamic analysis paths, then synthesise a valid input from scratch.

Phase 1 — Triage

file ./indirect
indirect: ELF 32-bit LSB executable, Intel 80386, not stripped

nm ./indirect | grep check
080491a2 T check_a 080491b4 T check_b 080491cc T check_c 080491e4 T check_d

nm -D ./indirect
U printf@GLIBC_2.0 U strlen@GLIBC_2.0

Triage reveals four named check functions and strlen in imports — a strong signal that length validation is part of the scheme. No password in strings; the logic is distributed across multiple functions rather than a single comparison.

Phase 2 — The Indirect Call

Inside validate(), IDA shows the function pointer array being constructed on the stack, then dispatched through a loop:

IDA — validate() dispatch table setup
; Build function pointer array on stack
lea     edx, (check_a - 804BFF4h)[eax]
mov     [ebp+var_1C], edx
lea     edx, (check_b - 804BFF4h)[eax]
mov     [ebp+var_18], edx
lea     edx, (check_c - 804BFF4h)[eax]
mov     [ebp+var_14], edx
lea     eax, (check_d - 804BFF4h)[eax]
mov     [ebp+var_10], eax
IDA — validate() loop body
loc_8049263:
mov     eax, [ebp+var_C]            ; loop counter i
mov     eax, [ebp+eax*4+var_1C]    ; load checks[i]
sub     esp, 0Ch
push    [ebp+arg_0]               ; push input
call    eax                        ; ← indirect — IDA cannot resolve statically
add     esp, 10h
test    eax, eax
jnz     short loc_8049280

The critical instruction is call eax. IDA cannot determine the destination at static analysis time — the call graph for validate() shows no outgoing edges to the check functions. In a stripped binary with runtime-computed addresses this would be a dead end for static analysis alone.

Phase 3 — Static Recovery

Because this binary is not stripped, IDA labels the function pointers by name in the dispatch table setup. Opening each check function directly reveals their constraints:

check_a
s[0] == 'X'
cmp al, 58h
check_b
strlen(s) == 6
call strlen / cmp eax, 6
check_c
s[5] == '!'
cmp al, 21h
check_d
s[1] + s[2] == 0xde
movsx / add / cmp eax, 0DEh

Phase 4 — Dynamic Recovery Path

In a stripped binary with runtime-computed function pointers, static recovery fails. The correct approach is to break on call eax and read the destination directly:

GDB + pwndbg
# Break just before the indirect call fires
pwndbg> break *0x8049263
pwndbg> run AAAAAA

# When breakpoint hits — read eax
pwndbg> print $eax
$1 = 0x80491a2        ← destination address

# Disassemble whatever eax points at
pwndbg> x/10i $eax
   0x80491a2 <check_a>: push ebp
   0x80491a3 <check_a+1>: mov ebp,esp
   ...
⚡ Key Principle

The CPU doesn't lie. Whatever obfuscation was applied to compute the function pointer, by the time call eax executes, eax holds the real address. Dynamic analysis cuts through any level of pointer obfuscation instantly.

Phase 5 — Input Synthesis

With all four constraints extracted, finding a valid pair for s[1] + s[2] == 0xde and assembling the final input:

Python — constraint solver
# Find printable pair summing to 0xde
for a in range(0x20, 0x7f):
    b = 0xde - a
    if 0x20 <= b <= 0x7e:
        print(f"s[1]={chr(a)} s[2]={chr(b)} sum={hex(a+b)}")
        break

# Output: s[1]=` s[2]=~ sum=0xde

# Assemble: X + s[1] + s[2] + [any] + [any] + !
key = "X`~aa!"   # s[3], s[4] unconstrained
print(key)
./indirect 'X`~as!'
[+] Valid.

Static vs Dynamic — Decision Rule

Symbols intact → read the dispatch table statically, open each target directly in IDA.
Stripped or runtime-computed → breakpoint on call eax, read $eax, disassemble destination.
Packed → dump after unpacking (follow OEP), then apply static path.

What I Learned

01 — call eax Breaks Static Analysis

Indirect calls via register prevent IDA from building a complete call graph. In stripped binaries this is a genuine dead end for static analysis — recognising it early saves time.

02 — Dispatch Tables Are Recoverable

Even when the call is indirect, the table construction that precedes it is often static. Following the lea + mov setup instructions before the loop reveals every destination.

03 — Dynamic Analysis Is the Fallback

A breakpoint on call eax with print $eax recovers any destination regardless of how it was computed. The CPU must resolve it — we just read the answer.

04 — Constraints Can Be Heterogeneous

Real validators rarely apply one rule. Four different checks — length, character value, arithmetic sum, positional — combined into one dispatch loop. Each must be satisfied independently.

05 — Opaque Predicates Die at -O1

Fake branches inserted for obfuscation are eliminated by the compiler when optimisation is enabled. Their presence (or absence) reveals the author's skill level and build configuration.

06 — Unconstrained Positions Are Free

Positions with no check applied (s[3], s[4] here) accept any value. Identifying which positions are free vs constrained is the first step in input synthesis.
